**Summary of type-risk items relevant to the Prisma docs' known SQLite→PG gotchas:**
- ❌ No `Int @id @default(autoincrement())` anywhere — avoids the classic autoincrement/sequence remap issue entirely.
- ❌ No native Prisma `Json` fields — avoids SQLite's TEXT-based Json emulation vs PG's native `jsonb` migration issue (AuditLog.payload is a plain String, unaffected).
- ❌ No `@db.Text` / native-type attributes present anywhere in the schema — Prisma will use its own default mapping per provider; changing provider will change the underlying column type Prisma generates (SQLite has no strict types; PG will get `TEXT` for `String` and `TIMESTAMP(3)` for `DateTime`) but this is transparent through Prisma Client.
- ✅ `Boolean` fields (7 total across Product/SlackSettings/Hold) — SQLite stores as `0`/`1` under the hood; PG has native boolean. Prisma handles the translation; no app code changes needed **except** the raw SQL in `src/app/api/products/route.ts` which manually does `Boolean(p.isLicensed)` etc. on raw query results — this assumes SQLite's `0`/`1` integer representation. Under PG with `$queryRawUnsafe`, boolean columns will come back as JS `true`/`false` already, so `Boolean(true)` still works, but the raw SQL query itself (LIKE, json_group_array/json_object) is SQLite-specific and **will break outright** on PG (see §5 for full detail — this is the single highest-risk file in the codebase).
- ✅ All `DateTime` defaults use `now()` (Prisma-level, portable) — no raw `CURRENT_TIMESTAMP` in schema.prisma (only in the generated SQLite migration files, which will be regenerated for PG).

4 matches found across 3 files:

| File | Line(s) | Query | SQLite-specific risk |
|---|---|---|---|
| `src/app/api/products/route.ts` | 29-68 | `prisma.$queryRawUnsafe` — full dynamic product listing query with string-interpolated `WHERE` clauses and a correlated subquery using **`json_group_array(json_object(...))`** | **HIGH RISK.** `json_group_array` and `json_object` are SQLite JSON1-extension functions with **no direct PostgreSQL equivalent** (PG's equivalents are `json_agg(json_build_object(...))` or `jsonb_agg(jsonb_build_object(...))`). ## 9. Risks & Compatibility Notes

- **Case sensitivity (identifiers):** Postgres folds **unquoted** identifiers to lowercase; Prisma always generates properly double-quoted identifiers (`"Product"`, `"priceCents"`, etc.) in its own queries and migrations, so Prisma Client calls are unaffected. However, **hand-written raw SQL that omits quotes** (e.g., `scripts/health-check.ts`'s `FROM Product`) will break because `Product` unquoted resolves to `product`, which won't match the actual `"Product"` table. Every raw-SQL file in §5 must be audited for unquoted identifiers.
- **Case sensitivity (string comparison / `LIKE`):** SQLite's `LIKE` is case-insensitive by default for ASCII text; PostgreSQL's `LIKE` is case-sensitive (use `ILIKE` or `citext`/`lower()` wrapping for parity). This directly affects the product-search feature in `src/app/api/products/route.ts` (§5) — search-by-name/brand/description will become case-sensitive unless explicitly fixed.
- **JSON storage/aggregation:** SQLite's JSON1 functions (`json_group_array`, `json_object`) used in the product-listing raw query have no drop-in PG equivalent; must be rewritten using `json_agg`/`json_build_object` (or `jsonb_agg`/`jsonb_build_object`) as part of the swap, not an afterthought — this endpoint will 500 on PG otherwise.
- **Boolean representation:** SQLite stores booleans as integers (0/1); the raw-SQL result mapping in `products/route.ts` does `Boolean(p.isLicensed)` defensively, which continues to work under PG (native `true`/`false`) — no change needed there specifically, but worth re-testing once the query itself is rewritten.
- **Indexes:** All indexes in the schema (`@@index([...])`, `@@unique([...])`) are simple B-tree-compatible column indexes with no SQLite-specific collation or partial-index syntax — these should carry over 1:1 via the regenerated PG migration with no manual intervention.
- **No native enums used:** All "enum-like" fields (`Product.status`, `Hold.status`, `HoldHistory.finalStatus`, `Admin.role`) are plain `String` columns constrained only at the application layer, not Prisma `enum` types — so there is no enum-migration complexity, but also no database-level guarantee against invalid values (pre-existing condition, unaffected by this migration).
- **Datasource `url` bug:** The current hardcoded absolute-path `url` in `schema.prisma` means `DATABASE_URL` env var is **currently dead code** — this must be fixed as the very first step of the actual swap (§8 step 2), otherwise every subsequent env-based configuration attempt will silently no-op.
- **Migration-lock/history:** Because all 4 existing migrations contain non-portable SQLite `PRAGMA`/rebuild SQL, there is no way to "convert" them in place — the correct approach (per Prisma's own guidance for provider switches) is to archive them and generate one fresh baseline migration against the new provider, accepting the loss of granular migration history for the SQLite era (acceptable since this is pre-production).
- **`package.json` DATABASE_URL overrides:** `db:reset` and `db:reset-full` scripts explicitly hardcode `DATABASE_URL=file:./prisma/dev.db`, which will silently keep those two scripts on SQLite even after the schema/env switch, unless updated — a likely source of confusing "it works everywhere except db:reset" bugs if missed.
- **Stray nested `prisma/prisma/dev.db`:** Indicates some prior script was run from an unexpected working directory relative to a `file:./prisma/dev.db` URL; worth a quick sanity check that no `package.json` script or CI step still has this risk before/after the PG swap (once `DATABASE_URL` is env-driven and absolute, this class of bug goes away).
- **Env var provider ambiguity:** README says Neon, `.env.example` says Supabase — purely a documentation/process question to settle before creating the actual production `DATABASE_URL`, not a technical blocker for schema-level work.
